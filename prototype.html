What's AI-generated

Hero line — phrases the deal in human terms using giver name + deal category. Never invents merchant facts.

Scene paragraph — composes merchant context (hours, what to expect, location color) from structured fields. Hard-blocked from inventing phone numbers, prices, or hours not in metadata.

CTA prompt — one calibrated sentence sized to the deal type's typical booking pattern. Tone matches the giver's note (warm if note is warm; neutral if no note).

What's not AI

The commitment-action options are deal-type-routed templates, not generated. The first action is always a primary CTA tied to the merchant's actual booking modality (online booking, phone, walk-in). AI suggests *which* option to lead with; it never invents booking links.

Why this design

The giftee is a brand-new, cold-start user. We have ~one screen to convert the gift into a planned action. AI's job is to remove cognitive load (what is this? what do I do?) by pre-doing the framing work the user would otherwise have to do alone. The commitment moment is the same Layer-1 mechanic from Part 1, deployed here because the giftee has the same problem as a direct buyer — plus less context.

Production guardrails

• Per-render eval against fact-check rules (no hallucinated merchant data).
• Tone calibration: model receives the giver's note tone as a hint, never a free-form copy target.
• Fallback: if merchant metadata is incomplete, fall through to a static template — never ship empty-field generation.
• Human review on the eval set (200 deals) before global rollout. Reviewers can flag tone, accuracy, and any cultural misfires.

How this would work in production

The Welcome is rendered server-side on giftee landing. The model call is a single structured generation against deal + giver + giftee context. Latency budget <1.2s p95; cache by deal_id + giver_note_hash for re-renders (purchaser preview uses the cached output so what they see at gift purchase is exactly what the giftee will see). All four AI-generated fields are constrained outputs — the model fills slots in a controlled template rather than generating free-form HTML.
Prompt schema (Claude-style) 
system: "You write welcome copy for a gift recipient landing on Groupon for the
        first time. Voice: warm, concrete, brief. Never invent merchant facts.
        Use only the metadata provided. Match the tone of the giver's note if present."

inputs:
  giver_name: "Sarah Mitchell"
  giver_note: "Happy 30th, you wonder. Work has been BRUTAL — go get pampered."
  giftee_first_name: null         # only used if known from address book
  deal:
    title: "60-min deep-tissue massage"
    category: "local.health_wellness.spa"
    merchant:
      name: "Bliss Spa"
      neighborhood: "Wicker Park, Chicago"
      booking_modality: "online_booking_partner"
      booking_url: "https://book.blissspa.com/..."
      hours: { closed: ["mon"], typical_lead_days_weekend: 7 }
      review_count: 2140
      avg_rating: 4.7

outputs (structured):
  hero_line:        string, ≤16 words, mentions giver + experience
  scene_paragraph:  string, 50–80 words, factual context only
  cta_prompt:       string, ≤24 words, suggests urgency calibrated to lead_days
  cta_primary_label: string, ≤6 words, tied to booking_modality

constraints:
  - never include phone numbers, prices, or URLs not in the input
  - never assume relationship (sister, partner, boss, etc.)
  - if giver_note is empty, generate a neutral, deal-type-aware default
  - if any required merchant field is missing, return null and trigger template fallback
